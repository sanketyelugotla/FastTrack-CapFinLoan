3.2 System Architecture
CapFinLoan follows a gateway-first microservices pattern inspired by Domain-Driven Design principles. The Angular frontend communicates exclusively through the Ocelot API Gateway, which handles JWT validation and routes each path prefix to the appropriate backend service. Services communicate both synchronously (via HTTP for direct queries) and asynchronously (via RabbitMQ for event-driven workflows). Each service maintains its own SQL Server database, enforcing strict data ownership boundaries.
The architecture is structured in four distinct layers: the Client/Presentation layer comprising the Angular SPA, the API Gateway layer handling cross-cutting concerns, the Backend Microservices layer containing the seven domain services, and the Shared Infrastructure layer comprising RabbitMQ, SQL Server, and document storage. This layered approach ensures that concerns are cleanly separated, each service can evolve independently, and the system remains resilient to individual component failures.

3.3 RabbitMQ Messaging Architecture
Asynchronous messaging is a cornerstone of the CapFinLoan architecture. RabbitMQ, configured through the MassTransit abstraction library, enables decoupled communication between services without requiring them to be simultaneously available or to know each other's network addresses directly. This design improves resilience, scalability, and maintainability.
Three primary operational messaging flows govern the system's event-driven behaviour. In the OTP signup flow, AuthService generates a one-time password, hashes it with PBKDF2, stores it with a 10-minute expiry, and publishes an OtpSendEvent containing the plaintext OTP code, applicant name, and email. NotificationService consumes this event and dispatches the OTP email via SMTP. This decoupling means that even if NotificationService is temporarily unavailable, the OTP event will be delivered once it recovers, thanks to RabbitMQ's durable queue guarantees.
In the document status synchronization flow, when a document action (upload, verify, or reject) changes the overall document status for an application, DocumentService publishes an ApplicationStatusChangedEvent. ApplicationService consumes this command and updates its own database with the new loan application status. This maintains consistency across the domain boundary without requiring a shared database or direct HTTP coupling.
In the decision notification flow, after an admin approves or rejects a loan application, AdminService publishes a LoanApprovedEvent / LoanRejectedEvent containing the application ID, applicant details, decision outcome, sanction amount (if approved), interest rate, and decision timestamp. NotificationService consumes this event and sends a decision email to the applicant, ensuring they are promptly informed of the outcome.

3.4 Saga Choreography Design
CapFinLoan implements a choreography-based saga pattern to coordinate the loan lifecycle across multiple services. Unlike orchestration (which uses a central coordinator that explicitly directs each step), choreography relies on each service reacting to events published by other services. This approach avoids the single point of failure and complexity that a central orchestrator would introduce.
The saga begins when an applicant submits a loan application. ApplicationService transitions the record from Draft to Submitted status and publishes an ApplicationSubmittedEvent. DocumentService consumes this event, initializes the document checklist for the application, and publishes a ApplicationStatusChangedEvent. NotificationService consumes this to send the applicant an email listing the required documents.
Once the applicant uploads documents and DocumentService evaluates that all required documents are in a verified state, it publishes a DocumentVerifiedEvent. AdminService consumes this event in a trace-only capacity Ã¢â‚¬â€ critically, it does NOT automatically transition the application to UnderReview. The system intentionally requires a human-in-the-loop: the admin must manually click 'Mark as Under Review' in the admin review interface. This design decision reflects the real-world regulatory requirement for deliberate human oversight in lending decisions.
When the admin marks the application as UnderReview, AdminService publishes an ApplicationStatusChangedEvent. When the final approve or reject decision is made, AdminService publishes a LoanApprovedEvent / LoanRejectedEvent, which triggers the applicant notification email through NotificationService.
Saga state does not persist in a separate state machine or table. Instead, each service relies on its own domain state (the application status in ApplicationService's database, document statuses in DocumentService's database, and decision records in AdminService's database) as the authoritative source of saga progress. The CorrelationId carried in all saga events provides full traceability across service boundaries.
3.5 Authentication and Security Architecture
CapFinLoan implements a multi-layered security architecture designed to protect user data, secure API endpoints, and prevent unauthorized access. The system supports three distinct authentication pathways, each appropriate for different user scenarios.
3.5.1 OTP-Based Email Signup
New applicants register through a two-step process. In the first step, the applicant provides their email address and receives a one-time password via email (delivered asynchronously through RabbitMQ and NotificationService). The OTP is hashed using PBKDF2 HMACSHA256 with a 10-minute expiry window and stored in the AuthService database. In the second step, the applicant submits the OTP along with their registration details. AuthService validates the OTP hash, creates the user account, and returns a JWT token.

3.5.2 Google OAuth 2.0
The Google OAuth flow is handled entirely server-side for security. The Angular frontend obtains a Google ID token using the Google Sign-In (GSI) JavaScript library and posts it to AuthService. AuthService validates the token by calling the Google tokeninfo endpoint and verifying that the 'aud' claim matches the configured Google Client ID. For new users, an account is created with a null PasswordHash (no password is set). For existing Google users, a fresh JWT is issued. If an existing local (email/password) account shares the same email, a 400 conflict response is returned.
3.5.3 JWT and API Gateway Security
All protected API routes require a valid JWT Bearer token, validated at the Ocelot API Gateway level. The JWT contains the user's email and role claims, signed with HMACSHA256. The gateway performs token signature validation, and expiry checks before forwarding any request to a downstream service. Admin-specific routes require the ROLE_ADMIN claim in addition to a valid token. The Zustand auth store in the Angular frontend persists the token in sessionStorage and the Axios interceptor automatically attaches the Authorization header to every outgoing request.

3.6 Loan Application Lifecycle
The loan application lifecycle is the central business process of the CapFinLoan platform. It governs how a loan request progresses from initial creation through administrative review to a final credit decision. The lifecycle is implemented across three services Ã¢â‚¬â€ ApplicationService (owns the application record), DocumentService (owns document state), and AdminService (owns decisions and status history) Ã¢â‚¬â€ with coordination achieved through RabbitMQ messaging.
The lifecycle begins when an authenticated applicant accesses the 'Apply Loan' page, which presents a four-step wizard collecting Personal Information, Employment Details, Loan Details, and a final Review screen. The applicant can save a draft at any point without submitting, allowing them to return and edit the application. Once satisfied, the applicant submits the application with a declaration acceptance.
After submission, the application enters the DocsPending state following the first document activity (not immediately on submission). The applicant is expected to upload the four required documents: ID Proof, Address Proof, Bank Statement, and Income Proof. Each document upload is recorded in DocumentService's database with its own status (Pending, Verified, Rejected).
When an administrator reviews the application and verifies all documents, the application transitions to DocsVerified. The admin can then manually mark it as UnderReview to indicate active examination, and subsequently issue a final Approve or Reject decision. Approved decisions include a sanction amount and interest rate. Both decisions trigger an email notification to the applicant.

3.8 Frontend Architecture
The Angular 18 frontend is a single-page application built with Vite as the build tool and Tailwind CSS for utility-first styling. The application follows a page-based component architecture with a clean separation between applicant-facing pages, admin-facing pages, shared components, and service layer modules.
Route protection is implemented using two custom route guards: RequireAuth (which checks for a valid JWT token in the Zustand auth store) and RequireAdmin (which additionally validates the ROLE_ADMIN claim). The Axios instance is configured with a base URL pointing to the API Gateway and an interceptor that automatically attaches the Authorization: Bearer header to every outgoing request. A response interceptor handles 401 Unauthorized responses by clearing the auth store and redirecting to the login page.
3.8.1 Applicant Pages
The applicant-side interface consists of five primary pages accessible after authentication. The Dashboard page displays KPI cards summarizing total applications, pending/active applications, and approved applications, along with a table of the most recent five applications. The My Applications page shows all applications for the logged-in user with client-side search by name, status filter, and pagination at ten records per page.
The Apply Loan wizard is the most complex page, featuring a four-step form. Step 1 collects personal details (name, date of birth, gender, address, contact information). Step 2 captures employment details (employer name, employment type, monthly income, annual income). Step 3 records loan details (requested amount, tenure in months, loan purpose, remarks). Step 4 presents a full review before final submission with declaration acceptance.
The Application Detail page aggregates data from three parallel API calls Ã¢â‚¬â€ the application record, status history timeline, and documents Ã¢â‚¬â€ and renders a vertical status timeline alongside four document upload boxes. Document upload is enabled only when the application is in Submitted or DocsPending status. Documents are viewed through blob URLs generated from authenticated fetch requests.
3.8.2 Admin Pages
The admin interface provides four specialized pages. The Admin Dashboard displays six KPI cards reflecting the distribution of applications across all statuses, populated from the admin dashboard endpoint. The Applications Queue page shows a searchable, filterable, paginated list of all applications in the system. The Admin Review page is the core workflow interface, presenting full application details on the left, document boxes with verify/reject controls, and a decision panel on the right. The Admin Reports page visualizes application statistics using Recharts bar and pie charts and supports CSV export.
3.9 AI Chatbot Integration
A key differentiating feature of CapFinLoan is its integrated AI chatbot assistant, accessible to all authenticated applicants through a floating widget rendered in the bottom-right corner of every applicant page. The chatbot is powered by a locally hosted Groq API instance running the llama-3.1-8b-instant language model, with inference handled by ChatbotService acting as a proxy.
ChatbotService implements intent detection logic that classifies incoming messages before forwarding them to the language model. When an applicant asks about their latest application, all applications, applications by status, or a specific application by ID, ChatbotService fetches the relevant data from ApplicationService and includes it in the context passed to the language model. This allows the AI to provide accurate, personalized responses grounded in actual application data rather than generic information.

CapFinLoan strictly adheres to the database-per-service microservices principle. Each service that requires persistence owns its own SQL Server database, with no cross-service direct database access. 3.16 Reliability and Fault Tolerance
CapFinLoan incorporates several reliability mechanisms to ensure graceful handling of failures at different system layers. The MassTransit consumer retry policy automatically retries failed message processing up to three times before moving the message to a dead-letter queue. This handles transient failures such as temporary database unavailability or network timeouts without message loss.
Docker Compose health checks ensure that dependent services (SQL Server, RabbitMQ) are fully healthy before backend services attempt to connect. Services that consume from RabbitMQ are configured to wait for the broker's health check to pass, preventing startup failures due to race conditions. The API Gateway's Ocelot configuration uses container names for downstream service addressing, enabling Docker's internal DNS to resolve service locations dynamically.
For document upload failures, the DocumentService maintains a per-document status that allows partial retries Ã¢â‚¬â€ a failed upload for one document type does not affect the status of other documents. The Admin Review page disables decision buttons once an application has reached UNDER_REVIEW, APPROVED, or REJECTED status, preventing accidental duplicate decisions at the UI layer as well as the service layer (which enforces a unique constraint on ApplicationId in the decisions table).
